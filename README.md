# 🛡️ Linux Security Assistant

Pet-project на TypeScript / Node.js для исследования
Linux security monitoring, интеграции системных инструментов и
AI-assisted анализа security-событий.

Проект собирает события с одной Linux workstation из нескольких
источников, выполняет базовое детектирование и предоставляет
естественно-языковой интерфейс к журналу событий. Ответ можно
озвучить через Piper TTS.

> **Pet-project / technical demo.**
> Проект не является заменой EDR или SIEM.

## Идея

Основная идея проекта — посмотреть, как можно объединить несколько
независимых инструментов безопасности в один небольшой application
layer и сделать работу с результатами удобнее для человека.

```text
auditd ──────┐
ClamAV ──────┤
UrlGuard ────┤
CommandGuard ┤
              ↓
           Logger
              ↓
        security events
              ↓
      ┌───────┴────────┐
      ↓                ↓
AnomalyDetector    AI Assistant
                       ↓
                    Ollama
                       ↓
                   Piper TTS
```

## Что умеет

- **DownloadsWatcher + ClamAV** — автоматически проверяет новые файлы в `~/Downloads`
- **AuditdBridge** — получает события Linux audit subsystem
- **CommandGuard** — перехватывает опасные shell-команды (`rm -rf`, `dd`, `mkfs`)
- **UrlGuard** — проверяет ссылки через VirusTotal, использует whitelist и cache
- **AnomalyDetector** — обнаруживает простые аномалии по детерминированным правилам
- **Logger** — приводит события разных источников к единому формату JSONL
- **LogQueryService** — фильтрация и поиск событий
- **Ollama + Qwen2.5 3B** — естественно-языковой интерфейс к security-логам
- **Piper TTS** — голосовой вывод ответа

## AI pipeline

```text
Вопрос пользователя
        ↓
   QueryPlanner
        ↓
структурированный фильтр
        ↓
   LogQueryService
        ↓
  реальные события
        ↓
  AnswerGenerator
        ↓
      ответ
        ↓
      Piper
```

Ключевой принцип:

**Код отвечает за факты, LLM — за интерпретацию и выдачу.**

LLM не принимает решение о том, является ли событие угрозой.
Она преобразует вопрос пользователя в structured query, после чего
обычный код извлекает реальные события. Затем модель формулирует
понятный человеку ответ на основании этой выборки.

Для текущего проекта я сознательно не использовал embeddings/vector DB:
события имеют фиксированную структуру, поэтому детерминированная
фильтрация здесь проще и предсказуемее.

## Что оказалось интересным в разработке

### Auditd: состояние после перезапуска

Изначально уже обработанные события хранились только в памяти процесса.
После перезапуска состояние терялось, а `ausearch -ts recent` снова
возвращал старые события.

Сначала checkpoint был привязан к timestamp, но несколько audit-событий
могут происходить в одну секунду.

В итоге состояние стало храниться по audit event serial ID и
сохраняться на диск.

```text
audit event
    ↓
serial ID
    ↓
checkpoint
    ↓
restart
    ↓
не обрабатывать старые события повторно
```

Нативный `ausearch --checkpoint` оставлен как возможное дальнейшее
улучшение.

### Checkpoint пережил reboot, но не свой же формат

Serial-checkpoint из предыдущей сессии (`379774`) оказался больше,
чем serial после перезагрузки (`~140468`) — auditd сбрасывает счётчик
на каждом boot. Все новые события молча отбрасывались как "старые".

```text
serial-only        ❌ ломается после reboot
timestamp-only      ❌ коллизии внутри секунды
timestamp + serial  ✅ MVP-компромисс, timestamp первичен, serial — tie-break
```

Найдено и воспроизведено через живой прогон: сравнение вывода `ausearch`
напрямую с состоянием checkpoint-файла показало расхождение в разы.

### Defence in depth

CommandGuard работает на уровне shell, но сам по себе не является
надёжной границей безопасности: shell-level перехват можно обойти.

Поэтому он дополняется независимым auditd-слоем.

```text
CommandGuard
→ предупреждение / блокировка на уровне shell

auditd
→ независимый аудит системных событий
```

Идея — не полагаться на один механизм защиты.

### Разделение ответственности

По мере роста проекта чтение логов, поиск событий и security-логика
были разделены:

```text
FileLogEventRepository
        ↓
   LogQueryService
        ↓
   AnomalyDetector
```

Repository отвечает за получение событий из storage.

QueryService — за фильтрацию, подсчёт и группировку.

AnomalyDetector — за security rules.

### Dependency Injection

Зависимости создаются в `index.ts` и передаются через конструкторы.

```text
index.ts
   ↓
создание объектов
   ↓
constructor injection
```

Это позволяет компонентам не знать, как создаются их зависимости,
и делает архитектуру проще для дальнейшей замены компонентов.

### LLM как недоверенный компонент

Вывод QueryPlanner не используется напрямую.

Результат модели:

```text
LLM
 ↓
JSON
 ↓
validation
 ↓
LogQueryService
```

То есть LLM рассматривается так же, как любой другой источник
недоверенного внешнего ввода.

Содержимое логов также рассматривается как недоверенные данные:
оно отделяется от инструкций модели и не должно интерпретироваться
как команды.

### Человеческий фактор

Лог может содержать большое количество событий, и человеку сложно
одинаково внимательно просматривать большой поток информации в течение
рабочего дня.

AI в этом проекте не заменяет администратора, а добавляет ещё один
слой внимания:

```text
много событий
      ↓
детерминированная выборка
      ↓
AI анализирует конкретную выборку
      ↓
краткое объяснение человеку
```

Таким образом уменьшается вероятность пропустить важную информацию
при ручном просмотре большого количества событий.

## Архитектурный смысл проекта

Этот проект не ставит целью реализовать собственный EDR или SIEM.

Скорее это небольшая лабораторная модель следующего подхода:

```text
Security tools
      ↓
event collection
      ↓
normalization
      ↓
detection
      ↓
query / investigation
      ↓
AI-assisted analysis
      ↓
human decision
```

В реальной инфраструктуре такие задачи обычно распределены между
endpoint security, SIEM/XDR, threat-intelligence и automation-системами.

Следующий естественный этап развития проекта — интеграция с готовой
security-платформой вместо собственного локального сбора событий.

## Стек

TypeScript · Node.js · auditd · ClamAV · VirusTotal · Ollama · Qwen2.5 3B · Piper · chokidar

## Запуск

Системные зависимости: `clamav`, `auditd`, `ollama` (модель `qwen2.5:3b`), `piper` (+ голосовая модель `ru_RU`).

Установить зависимости:

```bash
pnpm install
```

Создать `.env` и указать:

```
VT_API_KEY=...
```

Запустить security-компоненты:

```bash
npx tsx src/index.ts
```

Запустить AI assistant:

```bash
npx tsx src/voice-repl.ts
```

Интеграционные тесты:

```bash
npx tsx src/test/integration-test.ts
```

## Статус

Текущая версия — завершённый учебный MVP и техническая демонстрация.

Основной интерес проекта для меня — не отдельные security-инструменты
сами по себе, а то, как их связать в единую систему, сохранить
надёжный поток событий, отделить security decisions от LLM и дать
человеку удобный интерфейс для работы с результатами.

В дальнейшем проект можно развивать в сторону интеграции с существующей
SIEM/XDR-платформой и использования локального AI как аналитического
слоя поверх централизованных security-событий.
